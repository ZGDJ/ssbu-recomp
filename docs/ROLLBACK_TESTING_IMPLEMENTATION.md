# Implementation prompt: private 1v1 test diagnostics

Implement M5.13 on an opt-in development branch, using the controlled versus 1v1 direction in ADR-0008 and FSD-016/019. Start from `feat/private-1v1-test-plan` or its verified successor. Read AGENTS.md, current ledger/handoff and relevant validation. Inspect active ownership and preserve unrelated edits. This brief is an implementation request, not a claim that the diagnostics already exist.

## Deliverable and user flow

A cousin launches `Play Rollback Test.bat`, plays with the engineer, and runs `Collect Rollback Logs.bat` even if the game freezes. Also expose a documented noninteractive PowerShell command with an optional session selection/output path. The collector works without a responsive game window, administrator rights, Python, Git or developer tools. It prints/shows the resulting unique ZIP path and a short instruction to send the file manually. Both players collect separately. Collection must finish with a useful partial bundle when the game/logs are unavailable and identify incomplete evidence. No automatic upload service is required.

Reuse `Collect Logs.bat`, `scripts/family_support.ps1`, the support GUI, launch/update tooling and their tests where appropriate; keep installer support working. The existing collector only allowlists installer logs. Its broad 32/64-hex redaction can remove match/build/checksum identities: use explicit schema-safe diagnostic fields and tested redaction instead of weakening privacy globally.

## Recording and collection

1. Inventory actual runtime log locations and launcher behavior. Add an identified test launch session and preserve startup/stdout/stderr, existing rollback/fight/crash/freeze reports, safe configuration and binary/package identity. Record actual executable bytes; source revision alone does not identify a stale binary. Make the test mode and unqualified status clear. Keep normal play behavior and installed saves separate.
2. Record bounded match start/configuration and failure events plus recent frame history. Use asynchronous/bounded recording with explicit dropped counts; retain startup metadata separately so rotation does not erase identity. The external collector reads shared/rotating files with byte/time limits and per-file error reporting, without RPC to the game, killing/suspending it, or requesting memory dumps. A hung writer may have unflushed records: label that limitation rather than inventing events.
3. Add a versioned JSON manifest and human summary: launch/session ID; shared match ID/epoch when available; peer and logical slot; source/package/executable identities; declared/applied rules and control profiles; active rollback/fallback mode/reason; memory admission/refusal and safe hardware summary; packet route/counters; actual/predicted input and correction/replay events; comparable confirmed-frame fingerprints with declared coverage and comparison counts; desync/fatal/watchdog evidence; missing/truncated/locked/rotated files and export limits. Correlate peers by match/epoch/frame, not wall clocks alone. For legacy builds export what exists and mark missing identifiers/features explicitly.
4. Export only allowlisted sanitized text/structured records. Exclude game data, generated game code, saves, keys/secrets, arbitrary environment/process listings and memory dumps. Preserve schema-validated diagnostic hashes. Mask user paths and sensitive endpoints/room codes while preserving consistent role/correlation labels within the report. The user chooses when to share the ZIP. Treat received ZIPs/log strings as untrusted data.
5. Supply an offline two-bundle inspector and an agent-facing triage note. Validate schema/integrity, safe archive paths and bounded extraction, build/config/session compatibility, completeness and overlapping frame coverage. Summarize initialization differences, active mode, first comparable divergence and input/restore failures. Report zero comparisons, absent counterpart, unmatched IDs, and legacy gaps explicitly. A matching limited hash does not prove full-state correctness; clean packet counters do not prove correct input application. Keep hypothesis distinct from diagnosis.

## Validation and stopping criteria

First deliver the standalone collector and identified logging path with existing telemetry; add runtime fields only where a specific comparison needs them. Use bounded packets with independent review for state/scheduling/protocol changes. Required runtime controls remain governed by VALIDATION.md.

Test a live writer, a simulated hung process, rotation, locked/missing files, empty startup, oversized/partial lines, stale/multiple sessions, disk/write errors, sanitization, path traversal and match/build mismatch. Verify bounded size/time and explicit missing-data outcomes. Test synthetic mismatched timers, zero checksum comparisons, rollback resource refusal and invalid slot mapping as diagnostic inputs. Verify both GUI and CLI behavior and existing installer support. Actual new runtime recording requires measured overhead and applicable game checks; synthetic tests alone cannot qualify gameplay.

## Distribution

Use the named development branch as a starting source snapshot, not the cousins' normal update channel. Inspect `FAMILY-UPDATE.json` / installer metadata and updater code locally without exporting secrets; users may have ZIP installs rather than Git clones. Provide a separate test folder/channel with identifiable build, launch shortcut, copied disposable userdata and straightforward return to normal play. Pulling source alone does not rebuild or prove which executable runs. The two test PCs must use the same identified candidate and declared settings.

An early collector-only package may support legacy builds, with missing telemetry labeled. A runtime test package must pass applicable build/smoke/identity checks before instructions tell cousins to use it. Keep its experimental limitations visible. Commit and push the implementation branch to the verified fork, without merging into the ordinary family branch or publishing a release implicitly. Report exact commit, validation, artifact identity and tested installation instructions.

## Completion

Deliver collector/launcher/pair inspector, meaningful tests, a short tester guide and an agent triage guide. Update M5.13 and the current handoff with evidence and remaining limitations. The separate M5.12 setup task must synchronize/read back supported rules (including timer), establish two human slots and verify rematch ownership; log collection does not itself fix those defects. M5.14 retains actual two-PC 1v1 readiness gates. Four-member membership and mandatory delayed spectators belong to the later product phase.
