## Decision and verdict

The retained offline timing experiment does **not** demonstrate that the actual network initialization path lacks seed synchronization. That path already agrees a seed before original player-record construction, synchronizes stage context/history, reseeds the host random-byte stream, and seeds the global xorshift before the original constructor/selector. Consequently neither a late owner overwrite nor a new unconditional global reseed is justified as a network correction by the offline evidence alone.

The firm offline verdict is narrower: `SSBU_FIXED_SEED` controls startup entropy sources, not a per-battle seed contract. The first-fighter deterministic write is not the authoritative owner: original later reset reads owner `+0xf8` and replaces it. Original reset behavior is internally coherent, not itself a defect. If the desired fixture contract is independent of pre-match history, that requires an explicit battle-input policy, rather than treating the fixed entropy switch as that policy.

Smallest missing fact: **with the actual successful handshake path, equal agreed seed/rules/selected fighters and different pre-match histories, do selector entry/output, constructed owner seed, and later reset agree?** Existing handshake logs and origin/reset observers supply the relevant endpoints. This question directly selects whether network synchronization needs correction; the pre-wait menu observer does not answer it.

## Earlier decisions and correction boundaries

The host/join stage pick is already seed-dependent before construction. Original stage variation depends on a separate context seed/history/block; `RbhMatch` in `runtime/rb_hs.h:18–24` and `hs_apply` explicitly synchronize those inputs. Thus synchronizing only a script vector can never substitute for the existing earlier input contract.

Within the selector, player-record normalization and conditional duplicate-character handling precede the final global seed draw (`71014d8b54` calls `f_71014d9050`; `71014d8d3c..8ef0` call `f_710177fe70`). The inspected exact bodies of these two callees contain no direct global-xorshift advance; that observation is not exhaustive nested-call exclusion. The constructor also initializes/allocates context before the selector. No claim that the final seed draw is the first possible gameplay-relevant random decision is supported by this bounded audit. Wider consumer enumeration would not change the immediate decision to retain existing early network synchronization until its endpoints are tested.

- **Existing handshake boundary:** earliest implemented supported network input boundary; synchronizes original stage/context/global/OS inputs before player records and construction. Preserve it for the next experiment. It is not proven to exclude later intervening writers or asymmetric consumption.
- **Input `+0x98`, selection byte `+0x9c=0`, before selector:** original code supports retaining a supplied seed on eligible paths, so this is the smallest seed-specific input candidate. It preserves original owner copy/reset algorithms. However it skips the original global draw, does not synchronize earlier decisions, and selected-record paths can still replace it. A mode-zero-only hook is not justified. It also needs an explicit 64-to-32-bit seed mapping policy and exact hook identity; silently truncating the agreed seed would change semantics.
- **Selector-return input or post-copy owner write:** reliably later than selection, but excludes any earlier decisions made from the prior seed/context and changes initialization ownership after the original decision. Not preferred.
- **First-fighter or later-reset vector rewrite:** too late to govern earlier initialization and can erase legitimate RNG consumption. The observed frame-one equality/frame-two difference is exactly why this is not an initialization oracle. Removing this write may ultimately be appropriate for an original-initialization contract, but new runtime semantic behavior requires a justified fixture and validation, not an assertion that historical reference must still pass.

No production correction is proposed for immediate implementation on this evidence. The smallest supported *conditional* correction is to use the existing battle seed input with original selection disabled only if the network observation demonstrates that its owner seed still diverges and a checked eligible original path is established. If earlier synchronized decisions differ, that narrow input correction is insufficient; correct the earliest unequal initialization input instead.

## Lifecycle and mode scope

Every player-zero record setup invokes a new handshake and reapplies successful inputs, so the intended rematch contract is per setup, not per process. A failed handshake uses the local fallback and must not be mistaken for an agreed seed trial. `g_hs_seed` is only assigned on success in the inspected file, so its stale value after failure is not evidence of current agreement. Local Wireless and no-room-code local play return through `rbn_match_cancelled()==2` and bypass successful application. Loop mode bypasses handshake and may provide `SSBU_RB_NET_LOOP_SEED` at first-frame use only; it is not a substitute for the actual handshake experiment. Handshake-disabled network mode likewise does not prove this initialization path.

Battle owner and original vector are guest state; the success seed and random-byte stream are host state. Initialization must run at the new-match boundary, not whenever a snapshot is restored. Owner/vector restoration, host random-stream coverage, and replay across reset require their own evidence; a successful forward seed observation does not establish snapshot membership or atomic publication. M7.8 resource acceptance and M7.1's distinct membership/publication issue remain open. Astra B independently owns detailed lifecycle challenge.

## Smallest falsifying experiment

Decision: whether the existing successful network initialization boundary is adequate for the identified battle, or a seed-input correction is necessary.

At resource/network readiness, use the actual versus host/join handshake with a declared fixed nonzero network seed, same concrete fighters/rules and different pre-match histories. Preserve original reference separately. Reuse handshake logs plus the reviewed selector/constructor/reset observations; do not add a general consumer probe. Require confirmed current agreement, identified input mode/addresses, readable closed same-thread associations, complete fatal/trace/identity gates, then repeated uninstrumented runs and a second network seed. A two-process bundle must distinguish each peer and shared match identity; loop mode does not satisfy it.

Likely results and actions:

1. Equal selector entry/source, output, owner and reset: retain the current network seed synchronization. Test removal of the late vector override only as an independently justified original-initialization candidate; next gameplay gate is uninterrupted versus restore/correction when resource/state prerequisites hold.
2. Unequal selector global state after equal agreed reseed: bound the next observation to handshake application through selector entry. Correct the first unequal initialization input or asymmetric consumer; a forced owner seed alone cannot establish preservation of earlier decisions.
3. Equal selector source but unequal output/owner: compare existing mode/alternate-input records. Isolate selected-record branch or copy/later mutation before choosing the seed-input boundary.
4. Equal owner but unequal later reset vector: the proposed input correction is rejected; investigate reset selection/identity and concurrent/lifecycle state.
5. Read failures, absent agreement or resource refusal: preserve failed admission/control, make no network verdict, and run no further dependent trial.

Retain the original offline failed +60 reference result and historical reconstructed `f28f3988`; neither is reclassified. Fixed startup entropy alone is not a new battle fixture specification. Any new fixture needs an explicit per-battle seed meaning and retains historical comparison separately. Actual rollback still requires mandatory replay and an uninterrupted/all-correct-input oracle, not merely matching observed RNG.
