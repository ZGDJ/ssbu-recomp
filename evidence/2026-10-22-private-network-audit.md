# Private 1v1 networking audit and revised delivery plan

Date: 2026-10-22. Source inspection at HEAD `969a238d553ff600679c15ce7ddef5f977d21113` with pre-existing uncommitted thread/protection runtime, tests and documentation. No runtime edits or game trials were performed for this audit. Findings describe source paths, not measured network performance. Existing work and its claims are preserved; [ledger](../milestones/README.md) alone owns task status.

## Verdict

The checkpoint engine is not built around the wrong lobby: capture/restore work remains necessary and reusable. The network integration is coupled to the inherited lobby protocol and cannot yet be called transport-agnostic. General online direct-path support is not proof of direct rollback. Retain the engine and host/join candidate; specify and test private pair ownership/routing rather than starting a wholesale networking or GGPO rewrite. [ADR-0008](../adr/0008-private-pair-sessions.md) records the resulting direction.

## Source findings

1. `runtime/net_relay.c:478` (`net_rb_send`) wraps rollback as packet type 16 and sends to `g_lobby`. The ordinary direct-path sender later in that file uses peer candidates and freshness; rollback does not call it. External-lobby rollback therefore follows that endpoint, regardless of the ordinary direct-path option. This is a source-path finding, not packet-capture evidence.
2. `start_host` in the same file starts `net_minilobby.c` inside the host process and sets the host-side endpoint to loopback. For a two-PC host/join pair, this is an embedded forwarding service on one participant, not an extra Internet relay. It still has dispatch/queueing work; its cost has not been measured. LAN discovery and external NAT discovery are separate from rollback session admission.
3. `runtime/rb_net.c:270` (`rbn_handshake`) bypasses rollback for Local Wireless rooms by default. Normal host/join enters the rollback handshake through Smash versus; lobby/LAN modes without an explicit search override leave Smash local. A LAN transport option is therefore not equivalent to a qualified private LAN rollback product flow. Preserve inherited behavior while adding a distinct private rollback entry point.
4. `net_rb_send` chooses room peer, matchmaking peer or previously heard peer, with destination zero possible. Type-16 receive learns `g_rb_peer` from traffic, and filters against a matchmaking peer only conditionally. `rbn_rx` receives payload without a transport source argument. This is inadequate as the explicit active-pair boundary for a larger social lobby. Require selected-peer/session validation before handshake, liveness updates and queued input processing; do not assume private codes are authentication.
5. `runtime/rb_net.c:563` uses one remote (`1 - g_local`), resets two lanes, and later confirms from that remote's received-input horizon. Two active players are appropriate now, but lobby membership must not reuse this model. Fresh pair/session identity and safe terminal commit remain mandatory; input receipt alone is not corrected-state confirmation.
6. `net_stats_get` already uses `rbn_rtt_ms()` during an active rollback match. Preserve that useful distinction: it would be incorrect to claim all displayed ping is only lobby ping. General status and ordinary direct counters still do not prove the rollback route; add explicit rollback route/peer counters and timestamps.

Additional cross-checks: `net_minilobby.c:676-687` forwards destination-zero rollback packets within the same build/code partition. `rb_net.c:54-56` defaults host to slot zero and joiners to slot one; two guests cannot simply become a pair while retaining that assignment. `rbn_match_reset` resets coordinator state but does not clear `g_rb_peer`. The embedded lobby test at `tools/net/test_ssbu_lobby.py:334-337` skips stranger/public-broadcast rejection for its C variant. These findings justify production-connected admission/reset tests rather than relying on the lobby suite.

## What remains reusable

Retain the checkpoint ring, native continuation investigation, production-connected fault tests, strict trace comparators, frozen build manifests and refusal observers. M7.9 and M7.10 completed bounded source work; M7.8 remains in progress. Latest thread/protection evidence reports six passing control types after a preserved memory-shortfall failure. Arena/pad's learned membership refusal and setup/sweep's forward divergence remain unresolved evidence. None establishes complete authoritative state, multi-machine correctness, full roster or supported latency.

The current work is engine repair plus verification, not merely tooling. Do not discard it because networking needs a clearer boundary. Conversely, do not continue accumulating source-test counts as a substitute for the M2/M3/M4 deterministic-battle proof.

Record both peers, packet route and end-to-end measurements. No public matchmaking dependency. Test connection refusal, old epochs, stalled progress, disconnect and rematch. Pair 2-3 must not quietly route via waiting player 1 under a direct policy. First version shows waiting/status/results; live spectating is deferred. ## Required measurements and decision gates

Same-network Wi-Fi and cross-household Internet are separate supported-environment candidates. Record topology, hardware, software identities, access point/link conditions, route, RTT distribution, jitter/loss, input delay, stalls, rollback depths, p95/p99 catch-up and peak commit. Test both host assignments and real loss/reordering/bursts, since the existing delay simulator preserves order. Compare an external relay only as an explicitly selected diagnostic/fallback experiment, not a delivery prerequisite. Direct connectivity is the target, not a universal lowest-latency theorem.

A third waiting member must be unable to inject handshake/input traffic or contaminate the active pair's timing/epoch. Old-pair packets must be rejected on rotation before receipt bookkeeping. Lobby-owner departure has an explicit abort/close policy; automatic migration is deferred. No family rollout claim until its installation and gameplay gates pass.

## Owner clarification and revised delivery sequence

This same-day update supersedes the original three-member automatic-rotation/status-only proposal above, not the source audit findings. Target: one persistent code-based lobby with up to four members; any two activate controllers and select fighters, and up to two others watch mandatory delayed live playback. The implementation is location-independent. Cities are not architectural requirements; measured network conditions still bound support.

Order: engine safety and explicit private pair contract; deterministic offline battle proof; two-PC private versus rollback and route qualification; persistent in-game four-member lobby; bounded committed spectator stream and delayed playback; four-PC isolation/role-change qualification; first family-ready release after roster/performance and clean-PC gates. The ledger owns dependencies. M5.7/M5.8 are revised in place because they were unimplemented; M5.9-M5.11 add spectator work. M6.3 now waits for M5.11. Increased scope reflects the owner's mandatory first-release spectating requirement, not a new estimate of engine progress.

A lobby controller manages membership/code, active-pair readiness and viewer assignment. Initially it may run in the creator's game; no dedicated server is required. Pair handoff is automatic and preserves lobby membership/code. Controller never approves battle frames. Live spectators consume corrected committed inputs, cannot pin rollback history, and cannot backpressure battle sends/confirmation. Bound queues/locks/CPU/memory/bandwidth and shed viewer work rather than increasing fighter delay. Compare zero/one/two viewers in real battles under declared budgets. No promise of zero physical overhead is made.

Current F1 Experimental host/join and code fields are in-game controls; manual configuration-file editing is not required for ordinary setup. Retain versus-based battles rather than integrating Local Wireless synchronization. Router/firewall failure remains explicit. First-version defaults: mid-match arrivals may wait for next-match playback; owner departure may clearly close the lobby; automatic migration and simultaneous 3-4-player battles are deferred. Existing runtime work is untouched by this planning update.
