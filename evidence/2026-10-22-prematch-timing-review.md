## Phase and input reasoning

`runtime/nnhid.c:94-244` implements the tape. Before fighter registration it advances on player-one pad polls. `fighter_sdk/fighter_host.c:1413` changes this under deterministic mode to slot-zero fighter-frame deltas, unless DET_OFF bit 2 disables that behavior. `fill_pad` can consume multiple sequence ticks in one poll; equal tape suffixes are not a per-frame delivered-input recording. Record deterministic/DET_OFF settings, frame/poll diagnostics and actual suffix key order. Never call this authoritative input-history equivalence.

The retained 91-token controlled tape has character-selection navigation followed by `30:Z`, `90:Z`, `90:Z`, `@fight`, then `200` and the attack suffix. In prior current-b, zero-based key steps 14/15/16 were logged at polls 1592/1692/1792 with 586/592/31 draws; `@fight` step 17 was consumed at poll 2068. These are landmarks, not proven semantic names. In particular the final Z is already on a different draw range; blindly inserting before the last Z may delay loading or a later confirmation instead of the seed-producing menu action. Baseline selector/reset logs plus available step screenshots/scene evidence should locate the relevant earlier confirmation. Screenshot capture is of the next presented frame and is not an atomic key/scene sample.

`input_mark("fight")` is raised on first fighter registration in `fh_frame_line` (around lines 1291-1329), before incrementing that fighter's traced frame. It is not a menu, ready-go, constructor-entry or authoritative before-input boundary. Observer admission `frame0=0..3` includes construction before registration. Log line order across threads is useful bracketing but not a synchronized clock. Require same-thread call nesting where associating selector/reset events; do not infer absolute timing from merged log lines.

A bare neutral token `N` decrements `g_seq_left` for N ticks, then takes another tick to advance, so insertion adds **N+1 sequence ticks**, not N milliseconds or exactly N simulation frames. Increasing an existing key token's wait by N adds N ticks and preserves step indices, but is a different tape edit that must be declared explicitly. Either representation is acceptable if parent pins exactly one treatment, verifies no keys are held during it, preserves every other token/hold and the entire `@fight` suffix, and records actual observed step/poll deltas. A bare inserted token has no own step log; identify it through its neighboring logged steps and source semantics. Subsequent scene waits may absorb or amplify the global poll delta, so do not require every later absolute poll number to shift uniformly.

Existing deterministic mode itself writes a fixed nine-generator state at first registration unless DET_OFF bit 1 suppresses it (`fighter_host.c:1295-1314`). Preserve the prior configuration exactly: do not introduce reseeding or change DET_OFF to make the experiment discriminate. Equal first-frame folds can mask different pre-registration state; compare selector entry/source words and later owner/reset observations as well as the trace.
