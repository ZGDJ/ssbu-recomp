# SDK memory results and snapshot notifications

M7.8 continuation after [learned lifecycle](2026-10-22-learned-lifecycle.md). Caller review found that `os_AllocateMemoryPages` notified commitment even after failed `VirtualAlloc`, clearing `g_dc` for an absent page. A previously learned, decommitted page could then become a readable capture candidate. `os_FreeMemoryPages` notified decommit before an unchecked `VirtualFree` and returned success; failed decommit could leave live bytes represented as `RG_DECOM` by `rg_capture_collect`. These are source-derived failure sequences, not diagnoses of earlier game failures.

The SDK now notifies commitment only after OS success, retaining the existing `0x1015` allocation-failure result. Decommit retains pre-operation snapshot notification and cache invalidation, then checks `VirtualFree` before post-invalidation or success bookkeeping. Failure logs `SDK MEMORY FATAL` with operation/address/size/error and aborts. Release similarly checks OS success before post-invalidation/return. Pre-decommit ordering is intentional: the learned callback may reopen readonly pages; moving notification after successful decommit would fail that protection attempt and poison sticky tracking validity. The change preserves successful-operation ordering from pinned upstream `c7c874977ea7510c291ec8c278a58883a2f4e368`, but intentionally prevents continuation with false bookkeeping after OS failure.

The success mode checks failed allocation in untracked, learned, decommitted and learned-plus-decommitted modeled states, retaining metadata and guest bytes, and checks successful commit/decommit/release notification order. Fatal oracles assert that prenotification occurred, failed OS operations retained commitment/reservation, and no post-notification, accounting or return ran. Production SDK bodies and fatal helper are extracted exactly; OS, cache and snapshot callbacks are scripted. These tests do not execute the complete snapshot transaction or real OS allocation failures.
