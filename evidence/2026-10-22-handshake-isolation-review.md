## Decisive controls and interpretation

1. Source/disabled control: review and source-test policy, then original offline fixture with diagnostic absent/zero on the new candidate; require prior original reference, fatal, sealed 500 real/zero replay and identity gates. This rejects accidentally changed default execution.
2. Enabled handshake control: fresh actual host/join with same pre-match history, explicit seed 1, identical fresh saves/rules/modules, neutral suffix, existing origin/reset/early observations. Both must prove successful same-match handshake and complete records. This establishes instrument reach and reveals mode-specific initialization mismatch before the history treatment.
3. Change only one peer's declared pre-match history, keeping seed and battle inputs fixed; then repeat with a second nonzero seed. Equal selector entry and owner/reset outputs support retaining synchronization; entry inequality directs work to handshake-to-selector; equal observed entry but unequal outputs directs work to unobserved selector branch inputs/ownership, not a late reset patch.
4. Repeat the successful histories/seeds with observers disabled and repeated fresh processes. Preserve trace/fatal/identity checks. This tests whether logging hid instability, but an uninstrumented endpoint cannot prove the missing internal fields. Stop immediately on a failed control before expanding the matrix.

Each arm retains its historical-original comparison separately. Host/join changes the intended mode/seed, so mismatch with the old offline fixture remains a failed historical comparison rather than automatically diagnosing a mode defect. A new fixture needs an original-initialization semantic justification and identified uninterrupted counterpart; do not promote an instrumented mismatch into a replacement oracle. Full 500-frame agreement additionally requires equivalent applied battle inputs. Mandatory replay controls belong to actual save/restore work and must not be represented as passed by this zero-replay instrument.

## Endpoint limits and counterexample

`fighter_sdk/rng_seed_origin_probe.h:6-21` reads 160 input bytes but reports only mode, seed+0x98, select+0x9c, global RNG and alternate scalar, plus players/context addresses. It does not report contents selecting the selected-record branch. Two peers can have equal logged fields and unequal selected-record data; even matching final seed can mask different earlier branch decisions and RNG consumption. Treat equal observations as agreement on those endpoints only. If output differs with equal logged entry, the next smallest observation is the branch-selecting data for the reached case, not a universal RNG-consumer census. Existing samples are non-atomic and cannot prove which store ran.

Observer callbacks are process-scoped with frame-0..3 admission and finite count limits. Fresh processes bound the first experiment. Rematch requires explicit per-match observation identity/coverage; snapshot restoration remains outside this instrument. Equal RNG/vector telemetry also does not prove whole-state equality, same fighter/stage decisions, resource safety, or correction determinism.
