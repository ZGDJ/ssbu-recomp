## Exact sequence semantics

`seq_begin(15)` assigns index 15, clears `g_seq_holding`, clears run count and loads the next wait before calling `fight_rng_menu_boundary("begin",...)`. On this fixture it is reached from the end of step 14's ordinary key hold. This is **logical sequence release**, not proof that the guest has already received a released pad: `fill_pad` invokes sequence ticks before forming the returned buttons. No artificial neutral tick or input advancement should be added for observation.

Let step 14 confirmation occur at tick C. The existing code sets holding=1 and left=8 at C. Ticks C+1 through C+8 decrement and return while holding stays true. At C+9 the hold ends and step 15 begins. Thus the configured hold8 has nine sampled tick positions under this code; preserve that inherited behavior. At begin B, wait=W is loaded without being decremented that tick. B+1 through B+W decrement and return; confirm occurs at B+W+1, immediately **before** setting holding=1. Begin-to-confirm is therefore 91 or 151 ticks, and consecutive confirmation gaps are 9+91=100 or 9+151=160. These are source-derived sequence tick deltas, not elapsed seconds or authoritative simulation frames.

Before any fighter registers, `fight_seq_ticks()` returns one, so the intended window is one sequence tick per player-zero poll. Fighter admission changes that premise: deterministic mode can consume multiple sequence ticks in a poll. Require no fighters, no selector entry and same observer thread at both boundaries. The source counter/read/counter checks narrow but cannot eliminate races. Confirm is before enabling the key, not before every possible concurrent menu operation. The next-present screenshot is not an atomic sample of either boundary.
